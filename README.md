# mt-actions

Plugin action runtime for the [Edge-o-Matic 3000](https://github.com/MausTec/edge-o-matic-3000)
firmware. It loads `plugin.json` files (built by [mt-sdk](https://github.com/MausTec/mt-sdk) from
`.mtp` sources, e.g. [eom-plugins](https://github.com/MausTec/eom-plugins)), runs their event
handlers and functions, and dispatches calls to host functions registered by the firmware
(`src/actions/*.c` in the firmware repo).

The upstream repository (`MausTec/mt-actions`) is no longer published, which leaves the firmware
unbuildable. This is a reconstruction of the exact version pinned by firmware tag
**`v2.1.0-rc.1`** (submodule commit `9b7d6ed`, "Bump action runtime to v1.3.2"), recovered from:

* the official `v2.1.0-rc.1` firmware image (ESP32 / Xtensa), which is authoritative for the
  firmware-only parts (FreeRTOS event serialization, driver instances, plugin getters), and
* the WASM build of the same runtime in [`@maustec/mt-runtimes@1.0.0`](https://www.npmjs.com/package/@maustec/mt-runtimes)
  (`wasm/mtp-core.core.wasm`, published the same day, with a function-name section).

\* float→int overflow (e.g. `round(3e9)`) is undefined in C and differs by platform (the WASM build
yields INT_MIN, the ESP32 saturates to INT_MAX), so it is excluded from the suites.

## Layout

| Path | Contents |
| --- | --- |
| `include/mt_actions.h` | Public API used by the firmware |
| `include/mt_actions_internal.h` | Data structures (layouts match the shipped runtime) |
| `src/mt_actions.c` | Plugin lifecycle, config-save hook, builtin registration |
| `src/mta_args.c` | `mta_read_args`, argument coercion, variadic iterator |
| `src/mta_builtins.c` | `eq neq gt lt gte lte set add sub inc dec strcmp strlen charat getbyte setbyte mul div mod round chr to_string concat get_config set_config` |
| `src/mta_driver.c` | Driver instances (one persistent scope per connected BLE device) |
| `src/mta_exec.c` | Interpreter, variable resolution, errors, host dispatch, event invocation |
| `src/mta_parse.c` | Plugin JSON loader, config schema, action and condition parsing |
| `src/mta_pool.c`, `mta_scope.c`, `mta_hash.c`, `mta_value.c` | String pool, scopes, accessors, return helpers |
| `scripts/gen_plugin_api.py` | PlatformIO post-build step that writes `plugin-api.json` and `.sha256` |
| `test/` | Native test host, firmware-path tests, differential tests against the official runtime |

File names and function order follow the original: the WASM build preserves source order, and
the firmware's link order matches this alphabetical file list.

## Building the firmware with this library

### Prerequisites

* Git, Python **3.11** (what the upstream CI uses; very new Pythons break the ESP-IDF 4.4 tooling)
* About 2 GB of disk for PlatformIO's ESP-IDF 4.4.6 toolchain (downloaded on first build)
* **A checkout path without spaces.** ESP-IDF 4.4 refuses to build from paths containing spaces
  (for example `~/Documents/AI Projects/...`). Symlinks don't help, because PlatformIO resolves
  the real path.

### 1. Get the firmware at the matching tag

```sh
git clone https://github.com/MausTec/edge-o-matic-3000.git
cd edge-o-matic-3000
git checkout v2.1.0-rc.1
```

### 2. Point the `lib/mt-actions` submodule at this repository

```sh
git submodule set-url lib/mt-actions https://github.com/Xboarder56/mt-actions.git
git submodule set-branch --branch main lib/mt-actions
git submodule sync
git submodule update --init --recursive --remote lib/mt-actions
git submodule update --init --recursive        # the other submodules are still upstream
```

(To pin a release instead of tracking `main`, run `git -C lib/mt-actions checkout v1.3.2` and
commit the submodule change in your firmware fork.)

### 3. Build

```sh
python3.11 -m venv .venv
.venv/bin/pip install platformio
.venv/bin/pio run -e eom3k
```

Outputs, in `.pio/build/eom3k/`:

* `firmware.bin`: the application image (OTA / app partition)
* `bootloader.bin`, `partitions.bin`: only needed for a full flash
* `plugin-api.json`, `plugin-api.sha256`: host API descriptor generated by `scripts/gen_plugin_api.py`

The firmware embeds its version from `git describe` (`bin/pio/build_flags.py`). Building from a
detached checkout of the tag (as above) produces `2.1.0-rc.1+HEAD`, the same string as the official
release; building from a branch gives `2.1.0-rc.1` plus metadata.

### 4. Flash

With the device on USB:

```sh
.venv/bin/pio run -e eom3k -t upload          # app only
.venv/bin/pio run -e eom3k -t monitor         # serial console, 115200 baud
```

You can also install `firmware.bin` with the device's own update mechanism (SD card or OTA), the
same way as an official release.

### Installing plugins

Copy a plugin's `plugin.json` to the SD card as `/plugins/<name>/plugin.json` (or
`/plugins/<name>.json`). Per-plugin settings edited on the device are saved to
`/plugincfg/<name>.json`. Driver plugins (`"type": "ble_driver"`) attach automatically to BLE
devices whose advertised name matches their `match.ble_name` / `match.ble_name_prefix`.

## Running the tests

### Host tests (native, seconds)

Needs a C compiler and cJSON 1.7.15. ESP-IDF's copy or [upstream v1.7.15](https://github.com/DaveGamble/cJSON/tree/v1.7.15) both work.

```sh
make -C test CJSON_DIR=/path/to/cJSON                   # test/build/mta_host (trace replayer)
make -C test fwtest CJSON_DIR=/path/to/cJSON
test/build/fwtest /path/to/eom-plugins/drivers/lovense/plugin.json
```

`fwtest` exercises the paths that only exist on the device (per-plugin event lock and re-entrant
event queue, using a pthread FreeRTOS shim; driver instances; host-function permissions; missing
return detection; `to` captures). If `CJSON_DIR` is omitted, the Makefile uses
`~/.platformio/packages/framework-espidf/components/json/cJSON`.

### Differential test against the official runtime

Needs Node 20+, the official runtime package and the reference plugins:

```sh
mkdir -p /tmp/mtr && npm pack --pack-destination /tmp/mtr @maustec/mt-runtimes@1.0.0
tar xzf /tmp/mtr/maustec-mt-runtimes-1.0.0.tgz -C /tmp/mtr
git clone https://github.com/MausTec/eom-plugins.git /tmp/eom-plugins

# every reference plugin
python3 test/difftest.py --mta-host test/build/mta_host --runtimes /tmp/mtr/package \
    --work /tmp/mta-diff --plugins /tmp/eom-plugins

# edge-case suites (~160 single-action events, all builtins and error kinds)
python3 test/gen_atomic.py /tmp/mta-edge
python3 test/scenarios_edge.py /tmp/mta-edge
python3 test/difftest.py --mta-host test/build/mta_host --runtimes /tmp/mtr/package \
    --work /tmp/mta-edge /tmp/mta-edge/*.json
```

Each scenario is replayed through `test/mta_host.c` (this code) and `test/wasm_host.mjs` (the
official WASM runtime). The full traces are then diffed: every action enter/exit, condition, loop
iteration, host call with arguments, error message, return value and global variable.

`mta_host` also accepts `MTA_HOST_REGISTER=1` (route host calls through registered system
functions with the firmware's permissions instead of the unresolved-function handler). Build
`test/build/mta_host_rtos` and set `MTA_HOST_FIRMWARE_EVENTS=1` to also replay the firmware's
synchronous `mode_set` events on motor claim/release through the real event queue.

## Behavior notes

* **Event serialization.** Events for one plugin are serialized with a mutex. An event raised
  from inside a running handler on the same task (for example `mode_set` fired by
  `release_motor_control()`) is queued, up to 4 events with 4 args each, and runs right after the
  current handler. eom-plugins' `hw-api-smoke-test` trips over this: its queued `mode_set(0)`
  immediately undoes its own `lock_controls()`. The official firmware behaves the same way.
* **Plugin load memory.** The firmware's loader (`action_manager.c`, not part of this library)
  parses the whole `plugin.json` into a cJSON tree. Large plugins need several times their file
  size in free heap while loading.
* **Comparison builtins.** `eq`, `gt` and the other comparisons set `_` and also return 0 (true)
  or 1 (false). A bare comparison used as a statement in a function body therefore ends that body
  when false, because a status of 1 is treated as `return`.

## Differences from the shipped build

* The official image links its own copy of cJSON 1.7.15 ahead of the project libraries. This
  build uses ESP-IDF's identical `json` component, so cJSON sits elsewhere in flash. There is no
  behavioral difference.
* `plugin-api.sha256` is the sha256 of the generated file. The `fingerprint` values in the
  mt-runtimes catalog are computed by Maus-Tec's (unpublished) publishing step.
* Some functions where the original duplicated code inline use shared helpers here. That affects
  instruction-level similarity only.
